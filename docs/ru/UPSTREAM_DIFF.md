# Отличия серверной части (exit node) от upstream

Этот документ сравнивает код, который влияет на бинарник exit node и клиент
(desktop CLI), с текущим состоянием `p1neappleXpress/OpenFlux` (`main`, по
состоянию на 2026-09-12). Цель - понять, что именно ломает совместимость
между клиентом одной стороны и exit node другой, чтобы решить, что
синхронизировать, а что оставить как есть.

Android-приложение здесь не рассматривается: у upstream нет Android-клиента,
сравнивать не с чем.

> **Важно про ветки.** Всё ниже описывает ветку `experimental`, а не `main`.
> После синхронизации ядра с апстримом (`flx-kernel`) ветка `main` не
> содержит собственного фрейминга, обязательного шифрования и
> country-detection - она почти идентична апстриму и wire-совместима с ним
> "из коробки". Framing/DNS-relay/ping-graph/country живут только в
> `experimental` и требуют exit node на коде именно этой ветки. См.
> [FORK.md](FORK.md) про назначение веток.

## 1. `transport/encrypted.go` - критично, ломает совместимость целиком

В этом форке каждый пакет перед шифрованием оборачивается в 1 байт "тип
фрейма" (данные / ping-запрос / ping-ответ / DNS-запрос / DNS-ответ) - это
нужно, чтобы гонять пинг и (недавно) DNS-резолвинг в одном зашифрованном
канале вместе с обычными данными.

В смёрженном upstream PR `#38 upstream-pr-aes-gcm` (это тот же код, что и в
этом форке, но более ранняя версия - без фреймов) `Send()`/`Receive()`
работают с сырым plaintext без такого байта в начале.

Итог: если клиент этого форка шлёт пакет на exit node upstream (или
наоборот) - на приёме получается расшифрованный пакет с лишним байтом в
начале, IP-заголовок повреждается. Это касается не только DNS-relay -
вообще любой передачи данных, поскольку и режим туннеля, и Proxy-режим в
Android-приложении используют один и тот же код. Расхождение возникло ещё
на этапе добавления ping-фреймов, задолго до недавней работы над DNS.

## 2. Новые типы фреймов `frameDNSRequest`/`frameDNSResponse`

Отдельно от п.1: недавно добавлен резолвинг DNS через сам туннель - клиент
шлёт сырой DNS-запрос на exit node, тот стучится на upstream DNS-сервер по
UDP со своей сети и отвечает через тот же зашифрованный канал. Даже если
синхронизировать фреймовый протокол из п.1, эти два новых типа фрейма всё
равно должны присутствовать на обеих сторонах одновременно, чтобы
DNS-relay заработал.

## 3. Шифрование: обязательное vs опциональное

У upstream в `main.go` шифрование опционально: без `--encryption-key-file`
трафик идёт вообще без шифрования. В этом форке шифрование обязательно
всегда - без ключа процесс не стартует (принципиальная позиция форка, см.
[FORK.md](FORK.md)).

## 4. Транспорт `vyandex` (Volga)

У upstream он подключён к флагу `--transport vyandex`. В этом форке файл
`transport/yandex/vyandex.go` присутствует в дереве, но намеренно не
подключён к CLI-флагу - у него нет обязательной обёртки шифрования, и
включение противоречило бы модели "шифрование всегда" этого форка.

## 5. `tunnel/tunnel.go` - TCP-буферы gVisor

В этом форке `TCPBufDefault = 1MB`, `TCPBufMax = 8MB`; у upstream
`256KB`/`1MB`. Чистый тюнинг производительности, на протокол не влияет,
несовместимости не создаёт.

## 6. `tunnel/tunnel.go` - DNS-резолвер для `DialTCP`

В этом форке добавлен опциональный `SetDNSResolver` (использует
`EncryptedTransport.ResolveDNS` из п.2). Если резолвер не задан - как в
desktop CLI upstream - поведение полностью прежнее, локальный резолвинг.
Сама по себе эта часть обратно совместима; несовместимость возникает
только вместе с п.1/п.2.

## 7. `socks5/socks5.go` - авторизация и телеметрия

Добавлены: опциональная SOCKS5-авторизация по логину/паролю (RFC 1929),
счётчики переданных байт для отображения скорости в уведомлении, и
корректные ответы по RFC 1928 при IPv6-адресе или неподдерживаемой команде
вместо тихого разрыва соединения. Всё это работает на локальном SOCKS5-
сервере Android-приложения (Proxy-режим) - на протокол между клиентом и
exit node не влияет вообще.

## 8. `main.go` - определение страны exit node

Exit node этого форка при старте один раз стучится на `ip-api.com`,
определяет свою страну и публикует её клиенту через уже существующие
ping-фреймы (`EncryptedTransport.SetCountry`). У upstream этого нет.
Использует тот же фреймовый протокол, что и п.1 - тоже завязано на
совместимость.

## 9. `utils/debug.go` vs `utils/logging.go`

В этом форке добавлен `SetLogSink` (чтобы зеркалить debug-логи в
Android-приложение). Upstream переименовал файл в `logging.go` и добавил
`SetOutput` (редирект вывода). Разные, несовместимые между собой небольшие
доработки одного и того же места; ни на что критично не влияют.

## 10. iOS

У upstream снова появился iOS-код (`export_ios.go`, `export_ios_packet.go`,
`build_ios.sh`, `tunnel/packettunnel.go`). Этот форк его сознательно не
переносит (см. [FORK.md](FORK.md)) - iOS не поддерживается.

## Что действительно нужно решить

Пункты 1, 2, 3, 4 и 8 связаны друг с другом - все используют один и тот же
фреймовый протокол `EncryptedTransport`, и именно они определяют, сможет ли
клиент одной стороны вообще работать с exit node другой. Пункты 5, 6, 7 и 9
можно оставлять как есть без последствий для совместимости.
